# ps-records

**[English](README.md)**

프로그래머스 문제 풀이 기록. [programmers-tracker](https://github.com/BrokenFinger98/programmers-tracker)가 생성합니다.

## 구조

매 run·submit 이후 서버가 씁니다:

```
problems/<lessonId>-<title>/
├── README.md          프론트매터 + 시도 이력. 매번 덮어쓰기됨
├── notes.md           내 오답 노트. 서버가 절대 건드리지 않음
├── Solution.<ext>     최신 코드, 언어당 한 파일
├── examples.json      채점기가 준 예제 입력과 기대 출력
├── runner_test.<ext>  그 예제로 만든 실행기 — 아래 참고
└── attempts/          제출별 코드(NNN.<ext>)와 원본 프레임(NNN.raw.jsonl)
tags/<tag>.md          문제 유형별 노트 하나. 그 유형을 얼마나 만났는지가 적힙니다
dashboard.base         위의 전부를 훑는 Obsidian 표 — 아래 참고
log/submissions.jsonl  전체 제출 로그 (MCP 툴이 읽는 원본)
```

**`dashboard.base` 는 없을 때 딱 한 번 쓰이고, 그 뒤로는 건드리지 않습니다.**
[Obsidian Base](https://help.obsidian.md/bases) — 기록의 사본이 아니라 *질의문*이라 낡을 수가
없습니다. 표 일곱 개 — *Recent*, **Not passed yet**(아직 통과 못 한 것), *By attempts*, *By part*,
*By kind*(알고리즘/SQL), *By language*, *Tags*. 컬럼을 더하든 정렬을 바꾸든 그때부터는 여러분 파일이고, 서버는 다시 손대지
않습니다.

위의 나머지는 전부 매번 기록으로부터 다시 쓰입니다.

**`examples.json` 과 실행기는 둘 다 채점기가 준 예제가 있어야 만들어지는데, 그 예제는 *run*
에서만 옵니다** — 실행을 한 번도 누르지 않고 첫 제출에 통과한 문제에는 둘 다 없습니다. 한 번
실행하면 채워집니다.

실행기는 java, python3, cpp, javascript, kotlin, c, csharp에 대해 생성됩니다. 다른 언어는
생성되지 않고 서버가 그 이유를 로그에 남깁니다. 실행 명령은 파일 자체의 헤더에 적혀 있고
(`java RunnerTest.java`, `python3 runner_test.py` 등), **매 run 이후 교체되므로 직접 고친
내용은 사라집니다.** C#은 옆에 `runner_test.csproj` 도 함께 생성됩니다.

### 대시보드의 각 표가 무엇을 위한 것인가

파일 자체에는 이 설명을 주석으로 넣지 않았습니다. 일부러입니다 — **Obsidian은 `dashboard.base`
를 처음 여는 순간 다시 쓰면서 주석을 전부 지웁니다**(2026-08-14 실측: 뷰가 렌더링되는 그 순간
파일이 바뀝니다). 읽히면 사라지는 설명은 설명이 아니므로, 여기에 둡니다.

| 표 | 왜 있는가 |
|---|---|
| **Recent** | 최신순. 그건 주장이 아니라 사실이기 때문입니다. 나머지 정렬은 전부 여러분이 고른 관점이지 이 볼트가 내린 판정이 아닙니다 |
| **Not passed yet** | 이 도구의 존재 이유. 틀리고 다시 안 돌아온 문제는 프로그래머스 자체 기록에는 안 보입니다 — 거기는 "결국 풀었다"만 기억하니까요 |
| **By attempts** | 제출 수와 실행 수를 나란히. 20번 실행 후 1번 제출과 20번 제출은 다른 이야기이고, 한쪽 숫자만으로는 그게 안 보입니다 |
| **By part** · **By language** | 내 시간이 실제로 어디에 갔는지. 갔다고 생각하는 곳 말고 |
| **By kind** | 알고리즘과 SQL은 다른 연습입니다. 프로토콜이 다르고, 런타임이 비교 불가능하고, 복습 계획도 보통 따로 세웁니다 |
| **Tags** | 태그 지도를 표로. `catalogTotal` 이 정직함을 유지하는 분모입니다 — 카탈로그 전체에 문제가 1개뿐인 미접촉 태그와 38개인 미접촉 태그는 같은 공백이 아닙니다 |

오해하기 쉬운 두 가지. **Problem** 열은 파일 이름이 아니라 **폴더**입니다 — 문제 페이지는 전부
`README.md` 라서 폴더(`120802-<슬러그>`)가 식별자이고, 읽을 수 있는 제목이 앞에 옵니다. 그리고
**서버는 숫자를 쓸 뿐 그에 대한 판단은 하지 않습니다.** 이 표들 중 무엇이 약점을 보여주고 있는지는
여러분이 말할 몫입니다
([그 결정과 이유](https://github.com/BrokenFinger98/programmers-tracker/blob/main/docs/llm-wiki/wiki/decisions/2026-08-12-the-server-counts-and-names-nothing.md)).

## Obsidian 볼트로 보기

이 폴더를 볼트로 열면 그래프가 문제 유형을 보여줍니다. 문제마다 자기 태그로 링크가 걸려 있어서,
제출해 본 유형은 무리를 이루고 — **한 번도 제출하지 않은 유형은 홀로 떨어져 있습니다.** 그 고립된
노드가 핵심입니다. 내 기록만으로 만든 화면은 내가 만난 적 없는 유형을 보여줄 수 없으니까요.

`tags/<tag>.md` 각각에는 카탈로그가 그 유형으로 가진 문제 수가 적힙니다. 그게 그림을 정직하게
유지합니다 — 외딴 `tsp` 노드(카탈로그 전체에 문제 1개)와 외딴 `dp` 노드(38개)는 그래프에서
똑같이 보이지만 같은 발견이 아닙니다. 노트에는 **그 숫자가 나온 문제들의 링크**도 통과/미통과로
나뉘어 적혀 있어서, 유형을 누르면 실제로 붙잡았던 문제로 갑니다.

**노드 크기는 그 유형을 몇 개나 붙잡아봤는지입니다.** Obsidian은 링크 수로 크기를 정하는데 태그가
가진 링크는 내 문제들뿐이라, 큰 노드는 내 것입니다. 태그끼리는 일부러 잇지 않습니다 — 카탈로그가
같이 태깅한 것끼리 이어버리면 누가 쓰든 카탈로그의 허브 유형이 가장 큰 노드가 됩니다.

### 한 번도 안 만난 유형에 색 입히기

새 볼트는 외딴 점들의 벌판입니다. 아직 아무것도 안 만났으니까요. 그걸 잡음으로 읽지 말고 색을
입히십시오 — 그래프 뷰 설정(⚙)의 **그룹**에서:

| 검색어 | 표시되는 것 |
|---|---|
| `["status":"attempted"]` | **손댔는데 아직 못 푼 유형** — 빨간색이 어울립니다 |
| `["status":"untouched"]` | 한 번도 안 만난 유형 |
| `["status":"passed"]` | 한 번이라도 통과한 유형 |
| `path:problems` | 문제 자체. 내가 한 작업이 눈에 띕니다 |
| `["kind":"algorithm"]` | 알고리즘 문제 |
| `["kind":"database"]` | SQL 문제 |

태그 노트마다 `status:` 가 적혀 있는 게 바로 이걸 위해서입니다 — `attempted` 와 `solved` 를 한
단어로 합친 것이라, 색 그룹이 수식이 아니라 정확히 일치하는 검색 하나로 끝납니다. 전부 이
저장소가 이미 쓰고 있는 프론트매터를 읽습니다. 플러그인은 필요 없고, **저 색들 중 무엇이
중요한지는 여기서 정하지 않습니다.**

**알고리즘과 SQL은 색 두 개가 아니라 그래프 두 개로 나눌 수도 있습니다.** Obsidian은 설정을
패널마다 따로 기억하므로, 그래프 탭을 우클릭 → *오른쪽으로 분할* 한 뒤 한쪽 패널의 **필터** 에
`["kind":"algorithm"]`, 다른 쪽에 `["kind":"database"]` 를 넣으면 두 지도를 동시에 봅니다. 양쪽이
어느 정도 쌓인 뒤에 할 만합니다 — 프로토콜이 다르고 실행 시간을 서로 비교할 수 없어서,
`dashboard.base` 도 같은 이유로 둘을 나눠 놓았습니다.

`kind` 는 서버가 구독한 채널에서 옵니다. 그래서 **그 필드가 생기기 전의 기록에는 없고** 그 노트들은
어느 그룹에도 들어가지 않습니다. 그런 문제를 다시 풀기 전까지는 `["language":"mysql"]` 이 SQL 을
찾아 줍니다.

**시각은 서버가 도는 시계 기준입니다.** 트래커 `.env` 의 `TZ` 이고, 설정하지 않으면 UTC입니다 —
그러니 표의 시각이 통째로 몇 시간씩 어긋나 있다면 그건 수집 결함이 아니라 설정입니다. 설정 이전에
쓰인 행은 그때의 시계를 그대로 유지합니다. 어느 쪽이든 시점 자체는 정확하고, 보이는 방식을
바꾸려고 기록을 다시 쓰지는 않습니다.

**무엇이 구멍인지는 보는 사람이 정합니다.** 서버는 숫자를 적을 뿐 약점을 지목하지 않습니다 —
순위도, 문턱값도, "여기부터 하세요"도 없습니다. 그건 AI의 몫이거나 여러분의 몫입니다.

문제 페이지의 프론트매터에는 태그·레벨·판정이 들어 있어 Obsidian의 검색·속성·Bases가 플러그인
없이 그대로 동작합니다. Dataview는 필요하지 않고 쓰지도 않습니다.

⚠️ `.ps/` 는 트래커의 작업 상태입니다 — 아직 수집 중인 프레임, 문제별 타이머, 마지막 푸시가
언제 성공했는지. 자신이 설명하는 기록 옆에 있으라고 여기에 두었고, `.gitignore` 가 모든 커밋에서
빼냅니다. **절대 커밋하지 마십시오**: `.ps/raw/recorded/` 는 코드 실행 한 번당 파일 하나를
보관하는데, 한 문제를 푸는 동안 실행 버튼은 수십 번 눌리므로, 커밋하면 풀이 이력이 자기 자신의
연습 흔적에 파묻힙니다. `.gitignore` 가 이 규칙보다 오래된 경우 서버가 시작할 때 직접 추가합니다.
