# MCP — AI 클라이언트에서 내 기록 읽기

**[English](mcp.md)**

> 서버는 Model Context Protocol로 풀이 이력을 노출해 Claude, Cursor, 로컬 모델이 읽을 수 있게
> 합니다. **툴 여섯 개, 쓰는 것은 하나도 없습니다.** 넷은 저장된 기록과 집계를 그대로 돌려주고,
> 둘은 일정이나 순위를 계산합니다 — 계산하는 둘이 지키는 경계는 이 문서가 그것들을 보여주기
> 전에 먼저 말합니다. 만들어지지 않은 것은 맨 아래에 있고, 구현 상태의 authority는
> [README의 표](../README.ko.md)입니다.

## 엔드포인트

```
POST http://127.0.0.1:8080/mcp
X-Tracker-Token: <내 토큰>
```

Streamable HTTP이고, `/watch` 와 같은 프로세스·같은 포트입니다. stdio 브리지는 없습니다. stdio는
클라이언트 프로세스마다 서버 하나를 띄우는데, 이 서버는 살아 있는 채점 구독과 기록 저장소에 대한
배타적 락을 쥐고 있어 클라이언트마다 두 번째 사본이 존재할 수 없습니다.

### 토큰

**`/watch` 와 같은 로컬 토큰입니다.** 프로세스 하나, 자격 증명 하나 — 두 번째를 두면 복사하고
보호할 대상만 늘고 지키는 것은 늘지 않습니다. 둘 다 같은 프로세스를 지키니까요.

`TRACKER_WATCH_TOKEN` 을 설정한 적이 없다면, 서버가 첫 시작 때 하나를 만들어 소유자만 읽을 수
있는 권한으로 `.ps/watch-token` 에 저장했습니다. 이렇게 출력합니다:

```bash
cat .ps/watch-token
```

인증은 끌 수 없고 기본값도 없습니다. 이 엔드포인트는 풀이 이력 전체로 답하며, 루프백은 그 기계의
다른 모든 프로세스와 공유됩니다.

### 클라이언트 연결

대부분의 클라이언트는 URL과 헤더 맵을 받습니다. 형태는 이렇습니다:

```json
{
  "mcpServers": {
    "programmers-tracker": {
      "url": "http://127.0.0.1:8080/mcp",
      "headers": { "X-Tracker-Token": "<.ps/watch-token 에서 붙여넣기>" }
    }
  }
}
```

이 블록을 어디에 넣는지는 클라이언트 문서를 보십시오 — 클라이언트마다 다르고 릴리스마다 바뀌므로
여기에 옮겨 적지 않았습니다.

## 여섯 개의 툴

넷은 저장된 기록과 집계만 돌려줍니다. **어느 것도 해석하거나 순위를 매기거나 조언하지
않습니다** — 그것은 서버가 아니라 AI의 일이고, 빠뜨린 것이 아니라 규칙입니다
([`CLAUDE.md`](../CLAUDE.md), 설계 §7).

`review_queue` 와 `slow_passes` 는 무언가를 계산하며, 그 답을 읽기 전에 이들이 지키는 경계를
아는 편이 좋습니다: **일정을 잡고 순위를 매길 뿐 진단하지 않습니다.** 항목마다 그 날짜를 정한
사실들이 함께 실려 오므로 일정에 반박할 수 있습니다 —
[`decisions/2026-08-10-scheduling-is-not-diagnosis`](llm-wiki/wiki/decisions/2026-08-10-scheduling-is-not-diagnosis.md)
참고.

| 툴 | 인자 | 답하는 것 |
|---|---|---|
| `submissions` | `since?` · `verdict?` | 기록된 모든 run·submit, 최신순. 테스트케이스별 상세·컴파일러 출력·diff는 여기서 제외됩니다. |
| `get_problem` | `lessonId` | 문제 하나와 그에 대한 모든 제출을 전부 — 테스트케이스와 컴파일러 출력 포함. |
| `stats` | `groupBy` — `verdict` · `language` · `problem` | 버킷별 개수. 개수만. **제출만 세고 실행은 세지 않습니다.** **`problem` 은 언어를 합쳐서 셉니다.** |
| `list_problems` | `level?` · `part?` · `tag?` · `status?` | 내장 카탈로그를 기록과 조인: 문제별 `status`(`untouched` · `attempted` · `passed`)와 제출 횟수. |
| `review_queue` | `limit?` | 다시 풀 때가 된 문제, 가장 많이 밀린 것부터. 각 항목에 그 날짜를 정한 시도 횟수·도움 신호·통과일이 붙습니다. **언어당 한 항목입니다.** |
| `slow_passes` | `thresholdMs?` | 통과한 모든 문제를 가장 느린 테스트케이스(밀리초) 기준으로 정렬. 비교에 필요한 레벨·태그·언어가 함께 옵니다. |

`since` 는 날짜(`2026-08-01`)를 받으면 기록 자신이 지닌 오프셋으로 읽고, 오프셋이 붙은
날짜시각(`2026-08-01T09:00:00+09:00`)을 받으면 시점으로 읽습니다.

**두 표면은 의도적으로 다르게 묶입니다.** `review_queue` 와 `slow_passes` 는 (문제, 언어)를
키로 씁니다 — 통과는 그 언어를 증명한 것이므로, 자바로 풀었다고 코틀린 쪽 일정이 사라지지
않습니다([`decisions/2026-08-11-a-pass-belongs-to-its-language`](llm-wiki/wiki/decisions/2026-08-11-a-pass-belongs-to-its-language.md)).
`stats(groupBy=problem)` 은 문제별 제출 수를 세므로 언어를 합칩니다. "이 문제를 몇 번 제출했나"
가 그 그룹이 답하는 질문이기 때문입니다. 이걸 모르고 나란히 읽으면, 한 문제가 `review_queue`
에서 7개 항목이고 `stats` 에서 1개 버킷인 것이 모순처럼 보입니다. 다른 축은 `groupBy=language`
입니다.

**`stats` 는 제출만 세고 `submissions` 는 실행까지 돌려줍니다.** 같은 문제가 집계에서는 8,
목록에서는 15로 나오는 이유입니다. 실행은 시도가 아니며(설계 §5.1), 실행까지 센 판정 집계는
브라우저에서 코드를 쓰며 실행 버튼을 누른 것뿐인데도 컴파일 에러투성이로 읽혔습니다 — #235
전까지 `stats` 가 그렇게 답했습니다.

**"이 중에 한 번도 손대지 않은 게 뭐지"** 에 답할 수 있는 유일한 툴이 `list_problems` 입니다 —
기록만으로는 "시도했다가 틀림" 과 구분할 수 없습니다. 판정 집계에서는 둘 다 그냥 없으니까요.
필터는 모두 범위를 좁히기만 하고, 카탈로그에 없는 값을 지정하면 전부가 아니라 아무것도 나오지
않습니다.

### `review_queue` 가 말해주는 것과 말하지 않는 것

간격은 두 가지에서 나옵니다: 통과까지 몇 번 제출했는지, 그리고 막혀 있는 동안 질문하기 탭을
열었는지. **얼마나 오래 붙들고 있었는지는 반영하지 않습니다** — `focusedSec` 은 모든 항목에
실려 오지만 점수에는 들어가지 않습니다. 보정하려면 레벨별로 문제가 실제 얼마나 걸리는지의 분포가
필요한데 그런 측정이 아직 없기 때문입니다. 직접 판단하십시오.

브라우저 확장이 보고 있지 않을 때 기록된 통과에는 `sawQuestions` 키가 **없습니다.** `false` 가
아닙니다. 그런 항목은 가장 긴 간격에 도달할 수 없습니다. "우리가 안 보고 있었다"를 "도움을 안
받았다"로 읽는 것이야말로 불안한 문제를 두 달 뒤로 밀어버리는 단 하나의 오류이기 때문입니다.

네 밴드 뒤의 숫자 — 60, 21, 7, 3일 — 는 측정된 것이 아니라 고른 것입니다. 설계 §6.4가 제시하는
두 예시를 재현할 뿐, 그 이상은 아닙니다.

**통과는 그것이 쓰인 언어에만 유효하고, 다른 언어에는 아무 의미가 없습니다.** 같은 `lessonId` 가
서로 다른 `language` 값으로 두 번, 두 개의 일정으로 나타날 수 있으며, 한쪽으로 이어진 제출은
다른 쪽에 계산되지 않습니다. 회사가 평소 쓰는 언어를 지원하지 않아 Java를 연습하는 사람이,
Kotlin 통과가 그걸 덮었다는 말을 듣지 않도록.

한 번 풀었으면 다른 언어로도 "사실상" 쓸 수 있는지는 학습자에 대한 판단이고, 이 서버는 그런
판단을 하지 않습니다 — 일정만 잡습니다. 두 항목 모두 그 일정을 정한 사실들을 함께 들고 오니,
어느 쪽이든 동의하지 않는다면 정확히 왜 그런지 볼 수 있습니다.

### `slow_passes` 가 대신 정해주지 않는 것

설계 §6.5는 "같은 태그·같은 레벨의 문제들보다 현저히 느림"을 요구합니다. 그러려면 비교군이
필요한데 이만큼 어린 기록 집합에는 없습니다 — 그래서 **기준선을 적용하지 않습니다.** 분포 전체가
한 번의 호출로, 느린 순서대로 돌아오고, 선을 어디에 그을지는 여러분의 몫입니다.

측정값은 같은 이유로 **(문제, 언어)** 쌍에 속합니다: 실행 시간은 여러분이 푼 문제가 아니라
여러분이 쓴 풀이를 잰 것이니까요. 문제만으로 묶으면 가장 최근 통과 하나만 남아서, 빠른 Kotlin
통과 다음 날 쓴 느린 Java 통과가 사라졌습니다 — 이 도구가 드러내려고 존재하는 바로 그 측정값이,
그 도구 자신에게 가려진 겁니다.

**비교는 같은 언어 안에서 하세요. 그 이유는 측정된 것입니다.** 181952번 문제는 2026-08-12에
지원 언어 7개 전부로 통과했고, 그 답은 어느 언어에서나 한 줄입니다:

| java | kotlin | javascript | csharp | python3 | c | cpp |
|---|---|---|---|---|---|---|
| 83.33 ms | 65.19 ms | 36.28 ms | 22.42 ms | 10.74 ms | 1.17 ms | 1.12 ms |

**74배 차이이고, 그중 코드에서 온 건 없습니다.** 인터프리터와 VM의 시작 시간입니다. 언어를
가로질러 읽으면 이 목록의 맨 위는 "어느 런타임이 가장 늦게 뜨는가"이고, 한 언어 안에서 읽어야
이 도구가 하려는 일이 됩니다. 모든 항목에 붙은 `language` 필드는 고지용이 아니라 쓰라고 있는
것입니다.

`untimed` 는 각주가 아니라 답의 일부입니다. SQL은 테스트케이스별 시간을 아예 보내지 않고, 런타임
에러나 시간 초과는 케이스 단위로 시간을 떨어뜨립니다. 그런 통과는 "즉시"로 순위에 넣는 대신
순위에서 제외합니다. 없는 측정값을 0으로 정렬하면, 속도를 다루는 목록의 빠른 쪽 끝에 우리가 가장
모르는 문제들이 몰리기 때문입니다.

### `elapsedSec` 은 실제로 쓴 시간이 아닙니다

**문제를 처음 연 순간부터의 벽시계 시간**입니다 — 잠, 다른 일, 세션 사이의 며칠이 전부 포함됩니다.
타이머는 문제를 처음 본 시점에 시작해서 다시 시작하지 않으므로, 첫 대면부터 그 채점까지의
달력 시간입니다.

실측된 기록 하나:

```json
"elapsedSec": 77251,          // 21.5시간
"sensor": { "focusedSec": 37 }
```

밤새 열어둔 탭에서 30초 만에 푼 문제입니다. 두 숫자 모두 맞고, 서로 다른 질문에 답하며,
"얼마나 걸렸나"에 답하는 건 `focusedSec` 뿐입니다. 자릿수가 다를 수 있으므로 `elapsedSec` 으로
노력을 판단하면 틀리는데, **응답의 무엇도 그 틀림을 표시해주지 않습니다.** 기록을 돌려주는
도구들이 description 에서도 이 얘기를 하는 이유입니다.

`focusedSec` 은 확장이 보고 있지 않았으면 아예 없고, 그 부재는 0이 아닙니다.

`sincePrevSec` 은 셋 중 마지막입니다: **같은 문제의 직전 채점으로부터 지난 초**, 액션과 언어를
가리지 않습니다. 90초에 다섯 번 제출한 것과 사흘 저녁에 걸쳐 다섯 번 제출한 것을 갈라줍니다 —
찍기와 생각하기를요. 보고만 하고 점수화하지 않습니다. 직전 채점이 정말 없을 때만 null 입니다.

### 없는 데이터는 없어 보입니다

**기록되지 않은 필드는 답에서 아예 빠집니다** — 빈 문자열도, 0도, "Unknown" 도 아닙니다. 제목을
수집하지 못한 문제에는 `title` 키가 없습니다. `key` 가 없는 `stats` 버킷은 그룹핑 값이 기록되지
않은 제출들의 개수이며, 이는 "unknown" 이라는 이름의 버킷과 다릅니다.

이것은 들리는 것보다 중요합니다. 측정값처럼 읽히는 자리표시자야말로, AI가 있지도 않은 풀이 습관을
자신 있게 설명하게 만드는 원인입니다.

### 구멍이 있는 기록은 그렇다고 말합니다

**모든 응답**이 **어떤 기록도 대표하지 않는** 채점의 프레임이 잡혀 있을 때 `incompleteHistory` 를
함께 답합니다. 시작 프레임을 놓친 채점은 기록으로 만들 수 없고, 2026-08-11에 고친 결함들이
남긴 그런 채점이 작성자 머신에 두 건 있습니다. 이 필드는 해당 문제 번호와 프레임 수를 알려줍니다.

없을 때는 아예 나오지 않으므로, **있다는 것 자체가 신호입니다.** 예전에는 `stats` 에만 붙었고,
총계야말로 분모가 가장 중요한 자리라는 근거였습니다 — 맞는 말이지만 충분하지 않았습니다: 프레임이
고아가 된 통과는 `review_queue` 가 영영 잡아주지 않을 문제이고 `slow_passes` 가 순위에 넣을 수 없는
측정값인데, 둘 다 아무 말도 하지 않았습니다. 모든 도구가 같은 기록을 읽으니 모든 응답이 같은 구멍을
인정합니다. 응답에는 숫자만 담고, 설명은 각 도구의 description 에 있습니다 — 매 호출마다가 아니라
`tools/list` 에서 한 번 받습니다. 이게 있으면 같은 응답의 모든
개수는 불완전한 분모 위에서 센 것이고, 그 개수로부터 내린 결론은 그 사실을 말해야 합니다.
바로 위 문단과 같은 규칙을 한 단계 위에 적용한 것입니다 — 빠질 수 있는 건 필드만이 아니라
**기록 자체** 입니다.

복구되지 않으며, 그건 의도된 것입니다. 빠진 `start` 프레임이 테스트케이스 id와 문제의 공개
예제를 들고 있고, 고아 프레임 한 토막을 어느 시도에 붙일지는 추측이기 때문입니다 — 파일은
문제별 append-only 라서 여러 채점이 아무 구분 없이 이어져 있습니다.

## 프로토콜 개정

MCP에는 날짜가 붙은 버전이 있고, 형태가 바뀌었습니다: 개정 `2026-07-28` 은 `initialize` 핸드셰이크,
프로토콜 수준 세션, `ping` 을 없애고 프로토콜 버전을 매 요청으로 옮겼습니다. 이 서버는 **양쪽 시대

## 보안 태세

- 기본적으로 **루프백 전용** (`server.address`), 그와 무관하게 토큰은 항상 필요합니다.
- **`Origin` 헤더가 붙은 요청은 `403` 으로 거부합니다.** 네이티브 MCP 클라이언트는 보내지 않고
  브라우저는 보냅니다. MCP 명세가 요구하는 DNS 리바인딩 방어입니다. 필요하다면
  `TRACKER_MCP_ALLOWED_ORIGINS` 로 의도적으로 하나를 허용할 수 있습니다.
- **읽기 전용.** 툴들은 append도 move도 commit도 할 수 없는 쿼리를 통해 기록 저장소에 닿으므로,
  프롬프트에 주입된 "내 실패 기록을 지워라" 는 실행할 경로 자체가 없습니다.
- **프로그래머스 세션 쿠키는 어떤 로그 레벨에서도 이 경로에 오르지 않습니다.**
- 정상 경로에서는 아무것도 로그하지 않습니다 — 요청도, 응답도. 모든 응답이 풀이 이력의 조각이기
  때문입니다.

## 만들어지지 않은 것

설계 §7은 스무 개쯤의 툴을 스케치합니다. 없는 것 중 **스텁으로 만든 것은 하나도 없습니다**:
"미구현" 이라고 답하는 툴은 아예 없는 것보다 나쁩니다. 클라이언트가 `tools/list` 로 발견하고
그것을 전제로 계획을 세우기 때문입니다.

"만들어지지 않음" 이 서로 다른 네 상황을 감추고 있었으므로, 여기서는 나눠 둡니다 (#140):

**이미 가능함 — 툴을 추가하지 않습니다.** 데이터는 위의 툴들 안에 있고 묶는 일은 클라이언트의
몫입니다. 설계 §6의 첫 문장이 긋는 선이 바로 그것입니다.

| 스케치된 툴 | 대신 이렇게 |
|---|---|
| `attempt_diff` | `get_problem` 이 모든 기록에 `diffFromPrev` 를 담아 줍니다 |
| `stuck_testcases` | `get_problem` 이 `testcases` 배열 전체를 줍니다 |
| `performance` | `acceptanceRate` 와 `level` 이 모든 기록과 모든 카탈로그 항목에 있습니다 |
| `company_profile` | `list_problems` 가 689문제 전부에 `part` 와 `tags` 를 줍니다. 직접 묶으십시오. 회사 축은 **일부러** 만들지 않습니다 — `partTitle` 은 49가지 값이고 그중 절반가량이 학습 트랙이라, 회사로 묶으려면 프로그래머스가 언제든 바꿀 수 있는 라벨 위에 매핑을 손수 유지해야 합니다 |

**코드를 쓰기 전에 결정이 필요함.** 아래는 전부 쓰기이고, 여기서 읽기 전용은 범위 문제가 아니라
**보안 속성** 입니다: 토큰을 쥔 AI는 어떤 프롬프트를 받아도 풀이 기록을 바꿀 수 없습니다.

- `exam_start` · `exam_status` · `exam_finish`
- `append_retro`
- `push`

**삭제됨.** `warmup_plan` · `warmup_reset` · `warmup_report` — 설계 §6.3과 함께. 지난 문제는
범위 밖이기 때문입니다. `mark_hint` — #136에서 `hintLevel` 과 함께. 한 번도 측정된 적 없는데
측정값으로 제공되던 필드였습니다. `tag_problem` · `untagged` — 카탈로그가 분류된 채로 실립니다.

**정말로 없음.** MCP **resources**(`ps://…`)와 **prompts**. 서버는 `tools` 능력만 선언합니다.

페이지네이션도 없습니다: 인자 없는 `submissions` 는 로그 전체를 돌려줍니다. 한 사람의 오늘치
이력에는 괜찮고, 괜찮지 않게 되기 전에 한도가 필요할 것입니다.
